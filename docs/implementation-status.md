## Differences from the reference design

- Evaluation currently runs in the finalization job after all answers are submitted, rather than overlapping individual evaluations with the conversation. The evaluator still groups each main answer with its follow-up and applies the snapshot rubric.
- Question variation now uses 61 documented internal intent angles (21 HR, 20 User, 20 Manager), with separate persona prompts, CV evidence anchors and next-question adaptation from conversation. These are newly authored product guidance, not an externally validated question bank. See `question-guidebook.md`.
- New evidence matching requires literal quotations from a single source turn. Scores with no valid quotation are capped at 2/5, marked provisional and excluded from the new aggregate. The trade-off is that slightly altered quotations may be rejected.
- Original PDF and candidate answer audio are not persisted. PDF extraction and transcription use upload/request memory; clean CV text is retained. No raw answer-audio deletion job is needed.
- SQLAlchemy uses portable JSON and integer keys, including on PostgreSQL. Schema creation is automatic; the security update includes a transactional SQLite identity upgrade. There is no general-purpose production migration framework; the historical `sql/01_schema.sql` was not supplied.
- TTS is ElevenLabs-only and STT is OpenAI-only. Legacy alternate-provider settings in old docs do not activate fallbacks.
- Runtime emits request IDs, AI usage and failure-type events. It does not yet implement every historical timer or cost-estimation log field.
- The setup form starts empty apart from account profile values; no automatically inserted dummy CV/JD.
- Browser UI uses CSS bars for competencies instead of Chart.js. Dashboard API includes competency history; the UI shows aggregate stats and recent sessions.

## Validation and operations

The automated regression tests inject provider responses and use a temporary SQLite database. They cover configuration limits/snapshots, retry enforcement, response timeout cancellation, MP3 cache settings, provider error redaction, and the core session flow. PostgreSQL, Redis/arq and Docker have passed the Kiri integration smoke checks described above; load testing and a full paid-provider interview across the containerized worker remain unverified. In-process jobs are development-only and do not survive process termination. PostgreSQL row locks serialize concurrent turns across web processes; local locks also serialize answer work in the SQLite development server. Use PostgreSQL plus Redis for production.

Chrome smoke verification passed for login, responsive dashboard (390/768/1440px), session setup, synthetic camera/microphone checks, three recorded and streamed answers, finalization and desktop/mobile results.
